# ai-sdr -> dsh-sdr 迁移方案

## 目标与兼容范围

首个兼容目标为 DeepSeek Harness `0.1.0-rc.6`。rc.6 的模式菜单以 agent preset roster 为准，而 bundle 层不能直接向 shipped preset root 追加目录，因此当前版本采用受管 preset 安装器：bundle 激活时把 `presets/sdr` 安装到 `$DSH_HOME/.agent-presets/sdr`。安装后重启 `dsh web`，新建会话即可看到「SDR 数字员工」。

## 推荐架构

```text
DSH Web
  └─ SDR preset (persona + MCP client + native approval gate)
       ├─ mcp__sdr__* tools
       └─ sdr_review_drafts -> userQuestions -> loopback control
                                  |
                         Python FastMCP :8765
                                  |
             app/state.py + app/tools + RAG + SQLite audit
```

DSH 负责外层 Agent loop、工具编排和人机交互；Python 继续拥有业务状态机、数据访问、合规护栏、审批凭证和审计数据。MCP rc.6 只桥接 tools，不桥接 prompts/resources，因此 SOP 提示词放在 preset persona，业务动作放在 MCP tools。

## 代码边界

保留：`app/state.py`、`app/agent/`、`app/tools/`、`app/rag/`、`app/guardrails.py`、FastAPI、飞书接入，以及原有 Pydantic AI 运行方式。新增 `app/mcp/` 和 `app/storage/` 作为共享服务边界。

重写/新增：`packages/dsh-sdr/` 只负责 DSH bundle、preset、MCP client 配置、原生审批工具和受管安装。它不复制 Python SOP，也不把 RAG 实现搬到 Node。

删除：没有删除现有业务模块；没有凭证的外部发送实现保持 draft-only。未来若 DSH 提供正式 preset 安装 API，可替换安装器，但不应替换 Python 门控。

## 审批门控

MCP 公共工具不发布 `approve_email` 或 `send_email`。`sdr_review_drafts` 只能读取 loopback 待审批投影、调用 DSH `ctx.userQuestions.ask()`，再把人类选中的 `task_id`、`email_id`、`draft_hash` POST 到私有控制端点。Python `gates.py` 校验阶段、pending 状态和当前草稿哈希；`advance_after_approval` 在全部凭证批准前失败关闭；`send_email` 即使批准也只返回 `draft-only` 队列状态。

此外，preset 作用域内的 `ctx.tools.guard()` 拒绝模型直接调用任何 approve/send 名称。这个 guard 是附加防线，Python 门控才是权威约束。

## API 兼容与风险

- rc.6 的 MCP client 配置是一个插件实例一个 `serverName`，工具名会变成 `mcp__sdr__<rawName>`；不要假设 prompts/resources 会被消费。
- preset 只对新建或空白会话生效；已有会话需要重新创建。
- 受管安装器不能覆盖用户同名 preset。若检测到无管理标记的 `sdr` 目录，会保留用户版本并在日志中失败，需人工处理冲突。
- MCP 服务不可达时 `failOnStartupError=false`，模式仍可加载但业务工具为空；Python 服务应先启动，外部服务默认 dry-run。
- `ctx.tools.guard()` 是 agent 作用域的单调拒绝，不是网络隔离；loopback 控制端点必须只监听 `127.0.0.1`。
- DSH 的 profile/package 安装器会修改 `$DSH_HOME/profiles/<profile>`；验收应使用隔离 `DSH_HOME`，不要把带凭证的现有 profile 纳入提交。
